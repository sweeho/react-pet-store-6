# Design — Bootstrap, landing page and shared site shell

## Context

This change is generated by the platform for every migration and greenfield initiative (architecture doc 41). The idea canvas, its wireframes and its mockups are the detailed design; this document records the decisions every other capability relies on.

## Decisions

- **One shell.** Every page renders inside the same layout, header, navigation and footer. A capability adds content to the shell; it never draws its own chrome.
- **One navigation.** The global navigation lists every primary area and always links back to the landing page. A capability that adds a primary area adds one entry here rather than a second menu.
- **Shared states.** Empty, error and loading frames are components of the shell, reused by every page.
- **Existing boilerplate wins.** Where the repository already has an application scaffold, extend it rather than scaffold again.
- **Sign-in only if the product has it.** The shell carries a sign-in frame only when the product requirements call for authentication.

## Primary areas

- Localization (`localization`)
- Catalog browsing and search (`catalog-browsing`)
- Sign-on and access control (`sign-on`)
- Customer account and profile (`customer-account`)
- Shopping cart (`shopping-cart`)
- Checkout and order placement (`checkout`)
- Order approval (`order-approval`)
- Supplier inventory (`supplier-inventory`)
- Admin order and sales reporting (`sales-reporting`)

## Target design

### Components

- **Root landing page** `src/pages/index.tsx` (`/`, SWHR2-R-0288). PRD open question 3 treats the landing page and the storefront Home screen as one screen, so `/` renders the same Home screen component as `/petstore` (catalog-browsing owns its content). It links to every primary area: the storefront catalog, search, cart, account and sign-in, plus the Administration (`/admin`) and Supplier (`/supplier`) entries.
- **App shell** `src/components/shell/AppShell.tsx`: one layout with a header slot, the global navigation, a main content outlet and a footer (SWHR2-R-0290). Every page renders inside it. Pages add content and never draw their own header, navigation or footer.
- **Area layouts** `src/pages/petstore.tsx`, `src/pages/admin.tsx` and `src/pages/supplier.tsx` are `vite-plugin-pages` parent routes. Each wraps its area's child pages in `AppShell` and renders `<Outlet />`. The storefront layout fills the header slot with the storefront page header and the category side panel (sign-on SWHR2-R-0122, catalog-browsing SWHR2-R-0042). The admin and supplier layouts fill it with their own sign-out controls.
- **Global navigation** `src/components/shell/GlobalNav.tsx` (SWHR2-R-0289): one navigation, on every page, with one entry per primary area and a link back to `/`. A capability that adds a primary area adds an entry here rather than a second menu. Whether the Administration and Supplier entries belong in this navigation is PRD open question 3. This design includes them, because the spec requires an entry for every primary area.
- **Shared state frames** `src/components/shell/EmptyFrame.tsx`, `ErrorFrame.tsx` and `LoadingFrame.tsx` (SWHR2-R-0291). A page renders `EmptyFrame` when it has no data, `LoadingFrame` while its request is in flight, and `ErrorFrame` when its data cannot be loaded. `ErrorFrame` takes an `onRetry` callback and renders a retry control. Capability-specific empty text, such as the cart's "Your Shopping Cart is Empty.", is passed into `EmptyFrame` as its message.
- **Data hook** `src/hooks/useApi.ts`: wraps `fetch` for the JSON API and returns `{ data, error, loading, retry }`, so that every page maps those three states onto the three frames in the same way.

### Data

None. The shell holds no persisted data. The signed-on state and locale it displays come from the session endpoint owned by sign-on.

### Interfaces

- SPA routes: `/` (landing), `/petstore/**` (storefront), `/admin/**` (administration) and `/supplier/**` (supplier). Each is a file under `src/pages/` with no route registration.
- Consumes `GET /api/session` (sign-on) to choose between "Sign in" and "Sign out" in the storefront header.
- No API route of its own.

### Stack choices

- Vite React SPA with file-based routing through `vite-plugin-pages` and `react-router`, both pinned by the PRD constraints. Nested layouts use `vite-plugin-pages` parent-route files (`petstore.tsx` alongside `petstore/`).
- Tailwind CSS (CSS-first) and the shadcn/ui-style primitives in `src/components/ui/` for shell chrome. Icons come from lucide-react.
- React and react-router APIs are auto-imported by `unplugin-auto-import`.
- Tests: Testing Library UI tests for `AppShell`, `GlobalNav` and each frame; a Playwright spec asserting that the shell and navigation render on `/`, a storefront page, `/admin` and `/supplier`.
